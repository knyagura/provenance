# Provenance — Chain-of-Custody Threat Model

> **Update (2026-10-02): remediated.** Every finding in Part 1, plus the three highest-priority items from Part 2 (Witnessed Packing, parcel weight capture, Verifier Hub rotation/second-opinion), has been implemented in `provenance-prototype.html` and re-verified with scripted attacks (`attacktest.js`) and a full regression smoke test (`smoketest.js`), both passing. On top of the original findings, the user also required a mandatory dual-verifier rule for items over £1,500 and a full KYC + 2FA + always-audited identity/access layer — both implemented. See the "Remediation status" section at the bottom of this file for what changed, what's now genuinely fixed, and what residual limitations are honestly still present (inherent to a client-only mockup with no real backend).

This is a red-team pass over the custody chain built into `provenance-prototype.html`: Listed → Purchased → Verified → Packed → Sealed → Handed to carrier → (Luxury only: Verifier Hub arrival → authentication → reseal) → Shipped → Delivered → Unboxed → Confirmed, carried by the ProofSeal, the paired Item Seal, the Verifier Hub, and the optional Witnessed Opening add-on.

Two different kinds of weakness showed up, and it's worth keeping them separate. The first kind is specific to this prototype's code — things that are only true because the demo has no backend, and would be fixed by building the real system properly. The second kind is specific to the *design itself* — things that would still be true even with a flawless backend, because they're about physical materials, human incentives, or what a photo or a signature can actually prove. The first kind tells you nothing is broken that a real implementation wouldn't already fix; the second kind is where the actual design risk lives.

## Part 1 — Confirmed by scripted attack against the running prototype

Each row below was reproduced with a short Node/jsdom script that drives the live code (`window.selectItem`, `window.eval`, `buildHandoverSteps`, etc.) rather than guessed at. These are expected for a client-only mockup with no server — the point of running them is to make sure the *real* build doesn't inherit the same shape of hole.

| Finding | How it was demonstrated | Why it matters once this is real |
|---|---|---|
| **No trust boundary between client and "truth."** Setting every `state.timeline` flag to `true` directly (no handover, no hub, no unboxing) and reloading the Timeline and Item Passport screens shows a fully "Confirmed, funds released" order and a fabricated "Independently authenticated" Passport entry, with zero evidence log entries behind either. | `Object.keys(state.timeline).forEach(k => state.timeline[k]=true)` via console/`eval`, then `goTo('timeline')` / `goTo('passport')`. | In the prototype this is just a demo artifact of there being no server. In production it's the question that matters most: is "Confirmed" a status a browser can simply assert, or is it something only a server can set after checking signed, timestamped events it received independently from the seller's device, the hub's device, and the buyer's device? If the answer isn't "a server, from independent devices," the whole evidence chain is decorative. |
| **The ProofSeal/Item Seal "pairing" is two independent booleans, not a bound pair.** `state.pairing.paired` and `state.itemSeal.status` can be set to `true`/`'intact'` without ever running the handover flow, and nothing in the source ever compares `itemSeal.code` to `proofSeal.code` or stores a shared pair ID. | Flipped `state.itemSeal.status` to `'intact'` on a fresh order before handover; the UI still renders "fitted," and `grep`-ing the source for any code-to-code comparison or `pairId`/`pairedWith` field returns nothing. | The whole value of "two seals, registered together" is that a mismatched pair should be detectable. Right now the system would accept any two seals as "paired" as long as both status fields happen to be true — there's no cross-check that could ever actually catch an item swapped in transit. A real build needs an explicit pair record (both chip UIDs written to one row, checked at every scan) not two flags that are true in parallel by coincidence. |
| **The flagship anti-deepfake mechanism isn't actually in the flow.** The Protection page describes a "live, server-issued challenge code displayed on screen during recording" as the main defence against AI-generated video. Pulling the literal step lists for handover, Verifier Hub, and unboxing shows no step anywhere requires displaying, reading, or verifying such a code. | Dumped `buildHandoverSteps`, `buildVerifierHubSteps`, and `buildUnboxingSteps(...).steps` titles for the Dior item; none contain "challenge" or "code." | This is a gap between the pitch and the product. It's the single mechanism in the whole design that specifically defeats a pre-recorded or AI-generated clip — if it only exists as marketing copy and not as an enforced step, every other seal/scan/photo mechanic is still vulnerable to someone presenting fabricated footage, because nothing actually proves the footage was shot live. |
| **"Witnessed Opening" has no separate witness.** The courier's own confirmation step advances through the exact same `unboxingNext()` call, on the exact same device session, as every buyer-only step. There's no second login, device, or signature distinguishing "the courier attests this" from "the buyer clicked next." | Enabled the add-on, then drove all nine unboxing steps — including the two courier-labelled ones — with the same loop calling `window.unboxingNext()`; the "logged separately from your recording" confirmation appears regardless. | The entire pitch of this add-on is an *independent* human witness. As built, it's just two extra lines of text the buyer's own session can tick through alone — it adds no evidence a colluding or careless buyer couldn't fabricate solo. For this to be worth £7.50, the courier's confirmation needs to come from the courier's own authenticated app/device, not a step in the buyer's flow. |
| **Evidence log entries are unsigned client strings.** `state.handover.log` and `state.unboxing.log` are plain `{t, text}` objects pushed by client JS, directly editable (`state.handover.log[0].t = '03:00'`). | Logged three real handover steps, then overwrote the first entry's timestamp and text directly; the "evidence log" happily displayed the forged entry with no integrity check. | An "Evidence Timeline" is only as trustworthy as its weakest write path. If entries aren't timestamped and signed server-side at the moment each step completes, the log is just a diary the interested party writes about themselves — which is exactly the "my word against theirs" problem the whole concept exists to solve. |

## Part 2 — Weak points that survive a perfect implementation

These aren't bugs in the prototype — they're places where the *design*, even built flawlessly with a real backend, still rests on a physical material, a human incentive, or a single document that can be gamed. Several of these are visible in the prototype's own Dispute Centre example, which is a useful tell: that case ("box arrived empty") exists specifically because the seller's self-filmed packing wasn't independently witnessed and the buyer skipped Protected Unboxing — i.e. the sample dispute the prototype ships with is itself an illustration of weak point #1 below.

| Weak point | The actual risk | Possible mitigation |
|---|---|---|
| **No "Witnessed Packing" to match Witnessed Opening.** The buyer can pay £7.50 for an independent human to co-confirm the parcel is opened intact, but there is no equivalent paid option for an independent human to co-confirm what the seller actually put in the box. Carrier acceptance only logs that *a* sealed parcel changed hands, not what's inside it or its weight. | A seller who packs an empty or wrong box, seals it correctly, and hands it to carrier staff passes every seller-side checkpoint with no independent check on contents — exactly the asymmetry in the prototype's own sample dispute. | Offer the mirror-image add-on (independent witness or at minimum a weight/dimension capture) at the drop-off point, not just at delivery, especially for Luxury items that don't route through the Verifier Hub. |
| **Parcel weight is never a structured, automatic signal.** The Dispute Centre's own suggested next step is "ask the buyer for the courier's delivery weight record" — a manual, after-the-fact ask, not something captured automatically in the Evidence Timeline. Carriers already weigh every parcel for billing. | A cheap, hard-to-fake signal (expected item weight vs. actual parcel weight at pickup and at delivery) sits outside the evidence chain entirely, so disputes fall back on asking for it manually, after the fact, when it would be far stronger wired in automatically at pack time and delivery time. | Pull carrier weight/dimensions into the Evidence Timeline automatically at "Handed to carrier" and "Delivered," and flag mismatches before a dispute is even opened. |
| **NFC "breakable seal" security depends on the physical tag, not just the cut.** A one-time breakable loop only works as advertised if cutting it is the *only* way to read it. Passive NFC tags with a static UID and a tamper loop can, with modest equipment, be bridged (shorted) and read before the loop is cut, then cloned onto a second blank tag — producing a seal that shows a legitimate "intact → cut" transition in the app while its identity has been duplicated onto a tag that can be fitted to a counterfeit item. This is a known weakness class against counterfeiters who already clone luxury hardware. | This can't be solved in software; it's a component choice. A tamper-loop tag with a secure element and a monotonic, cryptographically-signed counter (verified against a server-side nonce at each scan) closes most of this gap — a bare passive NFC sticker with a tamper loop doesn't. | Specify the actual seal hardware (secure element + signed counter), not just "breakable NFC," in anything that goes further than this prototype. |
| **The Verifier Hub is a single named party and a single point of failure.** Everything about the Luxury tier's independence rests on one named facility ("Meridian Authentication Partners") doing the right thing every time. There's no mention of rotating hubs, random second-opinion audits, or anything that would catch an inside job, bribery, or simple negligence at that one facility. | Every Luxury transaction trusts one organisation absolutely. A single compromised employee or a complacent process at that one hub silently defeats the entire tier's premium guarantee, for every item that passes through it. | Rotate between at least two independent hubs, or require a random percentage of hub decisions to get a second, blind re-check — the point of "independent" is weaker if it's independent-but-singular. |
| **Discrete steps, not one continuous recording.** Both the handover and unboxing flows are modelled (and, presumably, intended to work in reality) as a sequence of separate confirmed steps rather than one unbroken take. That leaves room between steps to stop recording, stage something, and resume — splicing is much easier against five discrete clips than one continuous file with a running timestamp or hash chain. | Someone could legitimately complete every listed step while still editing out or substituting what happened in between them, because "between the steps" isn't itself part of the evidence. | Make the recording requirement explicit: one continuous file per leg, hashed and timestamped the moment it stops, with the discrete steps as chapter markers inside it rather than independent clips. |
| **No identity assurance anywhere in the chain.** The entire model proves what happened to *an item*, not who the seller or buyer actually are. A compromised or fake account can run every step of this flow completely legitimately from a process standpoint and still be fraud (stolen payment method, synthetic identity, a seller account taken over mid-transaction). | Chain-of-custody integrity and account/identity integrity are two different problems, and this design only addresses the first one. | Treat identity verification (even lightweight — matching payout details, device fingerprinting, re-authentication at high-value handover/unboxing moments) as a separate, explicit layer rather than assuming good custody evidence implies a legitimate counterparty. |
| **The custody chain goes dark between sales.** The Item Passport persists across resales, but there's no custody tracking at all while an item just sits with its owner between a confirmed delivery and the next listing — which is inherent to a resale marketplace, not a flaw unique to this design, but worth naming so it isn't assumed away. The passport is only as strong as whoever re-verifies the item at the *next* listing, and for Standard/Enhanced tiers that re-verification is light. | A substituted or damaged item can re-enter the passport chain cleanly if the next seller's self-reported condition isn't checked carefully, especially for lower tiers that skip independent verification. | Scale re-verification rigor to the *passport's* history, not just the current sale's price — an item with a Luxury-tier history arguably deserves at least a light hub re-check on every resale, even if the current sale price alone wouldn't normally require it. |

## If you only fix three things

Ranked by how much custody integrity rides on each one: first, make "Confirmed" something only a server can assert from independently-submitted, signed events — right now status is just client state, which undermines every other protection in the system at once. Second, give the Witnessed Opening add-on an actual independent witness — a courier confirmation entered from the buyer's own session isn't independent of anything. Third, bind the paired seals to each other with an actual shared record instead of two booleans that happen to both be true — otherwise "paired seals" is a narrative, not a check.

None of this is a reason to doubt the overall design — the seal, hub, and witness mechanisms are the right shapes to solve the problems in the original pain-point list. The gaps above are specifically the difference between a convincing prototype and a system a determined, well-resourced counterfeiter (the kind already capable of cloning luxury hardware) couldn't quietly route around.

## Remediation status (2026-10-02)

All five Part 1 findings and the top three Part 2 priorities are now implemented and scripted-attack-verified against the live prototype.

| Finding | Fix implemented | Verified by |
|---|---|---|
| #1 No trust boundary — client state can fabricate "Confirmed" | Every evidence log (`handover.log`, `verifierHub.log`/`secondLog`, `unboxing.log`, `attendantLog`, `courierLog`) is hash-chained via `pushSignedLog`/`verifySignedLog`. `verifySignedLog` now also requires a minimum entry count, so a log that was never actually written to (a forged "Confirmed" with zero real steps) fails verification rather than vacuously passing. `evidenceIntegrityOk(it)` aggregates all relevant logs for the active item; the Timeline shows an explicit "Evidence chain broken" panel once an order would otherwise display as confirmed, and the Passport withholds its "Independent authentication"/"Second independent authenticator" entries unless the chain verifies. | `attacktest.js` Attack 1 and Attack 5 |
| #2 ProofSeal/Item Seal pairing was two independent booleans | `state.pairing.proofSealCode`/`itemSealCode` now store the real codes written at handover; `sealsPairMatch()` compares live seal codes against that record on every later scan (hub, unboxing). A forged `itemSeal.status` with no real pairing now reads as unmatched. | `attacktest.js` Attack 2 |
| #3 Challenge code was prose-only, never an actual step | `challengeCodeFor()` + a "Read the on-screen challenge code aloud" step is now present in all three flows (handover, Verifier Hub, unboxing), each with its own cached per-leg code. | `attacktest.js` Attack 3 |
| #4 Witnessed Opening had no real independent witness | The courier now opens their own Provenance App session (own 2FA app-launch event, logged to the global `appAuthLog` under their own role) and their confirmation writes to a separate `unboxing.courierLog` hash chain, rendered in its own panel — not the buyer's `unboxing.log`. Honest residual gap, stated on the Protection page: this is still one visit/one physical device session, not fully separate hardware. | `attacktest.js` Attack 4 |
| #5 Evidence log entries were plain, directly-editable strings | `pushSignedLog` signs every entry with `simHash(prevHead|timestamp|text)` at write time; `verifySignedLog` re-walks the chain and fails if any entry's signature doesn't match, which also poisons every entry chained after a tampered one. | `attacktest.js` Attack 5 |
| No Witnessed Packing to mirror Witnessed Opening | New optional add-on (£4.50): an independent drop-off attendant inspects the item before packing and separately signs off once sealed, into its own `handover.attendantLog` hash chain, rendered in its own panel. | `smoketest.js` |
| Parcel weight never a structured signal | Weight is now captured at both pack (`handover.weighedKg`) and delivery (`unboxing.weighedKg`); `weightMismatchFlag()` surfaces a mismatch warning on the Timeline automatically, before either party has to ask. | `smoketest.js` (within-tolerance case); manually verified mismatch case during this remediation pass |
| Single named Verifier Hub, no rotation/second-opinion | `VERIFIER_HUBS` now has two named, independent partners. Luxury items under the new £1,500 threshold still get a random (34%) second-opinion audit from the second hub (`state.verifierAssignment.secondOpinion`); items over the threshold get it as a mandatory, policy-driven requirement (see new rule below), not a spot-check. | `attacktest.js` Attack 7 |

**New requirements added by the user during this remediation pass (not in the original threat model), also implemented and verified:**

- **Mandatory dual verification over £1,500.** `dualVerifierRequired(it)` returns true whenever an item routes through the Verifier Hub and is priced over `DUAL_VERIFIER_THRESHOLD` (£1,500). When true, the hub step list includes an unconditional "Second independent authenticator reviews the item" step naming the second hub (`Northgate Provenance Labs`), the Verifier Hub fee doubles (£22 → £44), and the Timeline/Passport show a dedicated second-authenticator entry. The demo's Dior bag was repriced to £1,850 specifically so this is actually exercised live, not dead code.
- **Account-level KYC + 2FA + always-on authentication audit log.** A global `state.identity` record (persists across item switches — deliberately placed outside `freshState()`'s reset) represents bank-style KYC: a government-issued photo ID matched against a live, in-app selfie liveness check, done once at account signup. `launchApp(role, note)` simulates a 2FA app-launch event (silent device-bound key + biometric as the normal path, with a step-up to a fresh ID/liveness check as a fallback) and is called — unconditionally, every time, never sampled — at the start of seller handover, hub inspection, buyer unboxing, and courier unboxing. Every call writes an entry to a module-level, hash-chained `appAuthLog` that is never reset; `verifyAppAuthLog()` re-verifies it. This is documented on the Protection page under a new "Identity & access" section.

**What's still honestly unresolved** (inherent to a client-only mockup, named rather than hidden): there is still no real server trust boundary — a determined attacker with raw console/DevTools access can still directly flip `state` flags, and the "fix" is that doing so is now *detectable* (fails integrity re-verification) rather than actually *prevented*. A real backend implementation would need to make these flags server-asserted from independently-submitted signed events, never settable from the client at all. Seal scan-count consistency (`sealScansConsistent`) is tracked in state but still has no dedicated UI surface showing "scans: N of expected M" — it's wired into the data model but not yet visible to a user or specialist. Witnessed Opening's courier confirmation is a separate login/log on the same visit, not separate hardware. NFC seal cloning via tag-bridging remains a hardware-specification question outside what software alone can close.
